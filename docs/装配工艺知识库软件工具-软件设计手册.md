## 1. 引言

### 1.1 编写目的

本文档旨在对"装配工艺知识库软件工具"（系统代号 OCR-Benti）进行全面的软件设计说明，涵盖系统架构、模块划分、数据模型、接口定义、核心业务流程与部署方案。文档面向软件开发人员、系统运维人员及项目管理人员，作为系统理解、维护和二次开发的技术依据。

### 1.2 系统概述

装配工艺知识库软件工具是一套**多视角知识建模与贝叶斯因果分析系统**，主要服务于机械加工与装配工艺领域的知识管理。系统核心能力包括：

- **知识可视化建模**：在交互式画布上以节点-关系图形式构建工艺知识概念网络
- **多源数据导入**：支持 OCR 图片识别、文本文件、CSV、Excel 以及达梦（DM）数据库等多种数据源的自动知识抽取
- **贝叶斯网络影响分析**：基于因果概率权重，进行上游追溯、下游传播和全局概览分析
- **多视角数据视图**：提供领导概览视角、工程师数据映射视角和工艺人员知识建模视角
- **多项目管理**：支持创建、切换和管理多个独立项目
- **用户认证与权限**：基于 Excel 用户表的登录认证，支持管理者与普通用户角色区分

### 1.3 术语定义

| 术语 | 说明 |
|------|------|
| 知识概念（Ontology） | 对工艺领域概念及其关系的规范化描述，系统中以节点（概念）+ 边（关系）的有向图表示 |
| 知识节点（Node） | 代表一个工艺概念或实体，如"切削参数""刀具材料"等 |
| 关系边（Edge） | 代表两个知识概念之间的语义关联，如"控制""影响""决定"等 |
| 父子关系（Parent-Child） | 特殊的层级关系，表示概念的包含与细分，如"机床"包含"主轴" |
| 贝叶斯网络 | 以概率权重标注关系边的有向无环图，用于因果推理分析 |
| 推理规则 | 传递性规则，如"若 A→控制→B 且 B→影响→C，则自动推导 A→决定→C" |
| 互斥规则 | 禁止在同一对节点间同时存在两种关系的约束规则 |
| 数据源（DataSource） | 外部数据来源，包括达梦数据库、Excel 文件、CSV 文件等 |
| 业务域（Domain） | 知识概念的逻辑分组，如"切削工艺域""质检域" |
| 视角（Perspective） | 面向不同角色的数据展示方式：领导概览、工程师数据映射、工艺知识建模 |

## 2. 总体设计

### 2.1 设计原则

| 原则 | 说明 |
|------|------|
| 前后端分离 | 前端 Vue 3 SPA 与后端 FastAPI RESTful 服务独立部署，通过 HTTP API 通信 |
| 离线优先 | OCR 引擎（RapidOCR）本地运行，无需联网；LLM 功能预留但默认禁用于内网环境 |
| 数据持久化 | 项目数据以 JSON 文件形式存储于文件系统，简单可靠，便于备份迁移 |
| 渐进增强 | 核心知识建模功能不依赖外部服务；数据库连接、LLM 识别等为可选增强功能 |
| 单一可执行文件部署 | 通过 PyInstaller 打包为单个 exe，包含前端静态资源、后端服务、OCR 模型 |
| 局域网协作 | 前端 Vite dev server 监听 `0.0.0.0`，API 通过代理转发，同一 WiFi 下其他设备可直接访问 |

### 2.2 技术选型

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| 前端框架 | Vue 3 | ^3.5.13 | 渐进式框架，Composition API 适合复杂交互逻辑 |
| 构建工具 | Vite | ^6.3.5 | 快速冷启动，原生 ESM 开发体验 |

| ONNX Runtime | onnxruntime | 1.10.0 | 跨平台推理引擎，Win7 兼容 |
| 图像处理 | OpenCV | 4.9.0.80 | headless 模式，仅用于图片解码和 OCR 预处理 |

### 3.3 部署架构

系统支持两种部署模式：

**开发模式**：
- 前端：Vite Dev Server（端口自动分配，默认 5173）
- 后端：Uvicorn（端口自动分配，默认 8000）
- 启动脚本：`start.bat` 自动检测可用端口并启动两个服务

**生产模式**（打包部署）：
- 通过 PyInstaller 将整个系统打包为单个 `OCR-Benti.exe`
- 前端构建产物（dist）嵌入 exe 资源中
- 运行时 Uvicorn 启动后端并同时托管前端静态文件
- OCR 模型、测试图片、预置项目均打包在内
- 兼容 Windows 7+

## 4. 模块设计

### 4.1 用户认证模块

#### 4.1.1 功能描述

提供基于用户名/密码的系统登录认证，使用 Excel 文件（`users.xlsx`）作为用户数据源，支持会话 Token 管理和角色区分。

#### 4.1.2 数据模型

**用户表结构（users.xlsx）**：

| 列 | 字段 | 类型 | 说明 |
|----|------|------|------|
| A | username | 字符串 | 用户名（唯一标识） |
| B | password | 字符串/数字 | 密码 |
| C | role | 字符串 | 角色：`admin`/`manager`（管理者）或 `user`（普通用户） |
| D | name | 字符串 | 显示名称 |

**会话存储**（内存）：
```python
_auth_sessions: dict[str, dict] = {}  # {token: {username, name, role}}
```

#### 4.1.3 接口设计

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/auth/login` | POST | 登录验证，返回 Token 和用户信息 |
| `/api/auth/logout` | POST | 登出，销毁 Token |
| `/api/auth/session` | GET | 校验 Token 有效性 |

#### 4.1.4 前端实现

- 登录页面使用现代设计风格，包含动效背景（OceanBreath）和封面图片
- 登录成功后将用户信息（Token、用户名、角色）存入 `localStorage`
- 应用启动时自动检查本地 Token 有效性
- 管理者（`role === "manager"`）可进行编辑操作，普通用户仅可浏览
- 侧边栏底部显示当前登录用户信息和登出按钮

#### 4.1.5 权限控制

| 功能 | 管理者 | 普通用户 |
|------|--------|----------|
| 浏览知识图谱 | ✓ | ✓ |
| 新增/编辑/删除节点 | ✓ | ✗ |
| 创建/编辑/删除关系 | ✓ | ✗ |
| 导入数据源 | ✓ | ✗ |
| OCR 识别导入 | ✓ | ✗ |
| 创建/删除/重命名项目 | ✓ | ✗ |
| 切换视角 | ✓ | ✓ |
| 贝叶斯分析 | ✓ | ✓ |

### 4.2 项目管理模块

#### 4.2.1 功能描述

支持创建、重命名、删除和切换多个项目。每个项目独立存储知识图谱数据（节点、边、推理规则、互斥规则、关系权重）、多视角配置以及上传的数据源关联信息。

#### 4.2.2 数据模型

**项目索引** (`backend/projects/index.json`)：
```json
[
  {
    "id": "uuid-string",
    "name": "项目名称",
    "created_at": "ISO-8601 datetime",
    "updated_at": "ISO-8601 datetime"
  }
]
```

**项目数据** (`backend/projects/{project_id}.json`)：
```json
{
  "nodes": [...],
  "edges": [...],
  "inference_rules": [...],
  "mutex_rules": [...],
  "relation_weights": {...}
}
```

**视角配置** (`backend/projects/{project_id}_perspective.json`)：
```json
{
  "project_name": "...",
  "domains": [...],
  "sources": [...],
  "mappings": [...]
}
```

#### 4.2.3 核心逻辑

- **初始化**：首次启动时若无任何项目，自动创建"默认项目"
- **数据迁移**：自动检测旧版 `data.json` 并迁移至项目存储
- **预置案例**：打包时内置"机械加工工艺案例"项目（`machining-demo`）
- **删除保护**：至少保留一个项目，防止全部删除
- **活跃项目**：全局变量 `_active_project_id` 跟踪当前选中项目

### 4.3 知识建模模块

#### 4.3.1 功能描述

提供交互式画布进行知识概念的可视化建模。用户可创建节点、建立父子层级关系、拖拽调整布局、连线建立自定义语义关系，并管理节点属性和关系特征。

#### 4.3.2 数据模型

**OntologyNode（知识概念）**：
```python
class OntologyNode(BaseModel):
    id: str                          # UUID 唯一标识
    name: str                        # 节点名称
    x: float                         # 画布 X 坐标
    y: float                         # 画布 Y 坐标
    parent_id: str | None = None     # 父节点 ID（层级关系）
    attributes: list[dict] = []      # 自定义属性 [{key, value}, ...]
    origin: str = "manual"           # 数据来源标识
```

**OntologyEdge（关系边）**：
```python
class OntologyEdge(BaseModel):
    id: str                          # UUID 唯一标识
    source: str                      # 源节点 ID
    target: str                      # 目标节点 ID
    relation: str                    # 关系名称（如"控制""影响""决定"）
    kind: "parent-child" | "relation"  # 边类型
    characteristics: list[str] = []  # 关系特征标签
    weight: float | None = None      # 贝叶斯因果权重（0~1），None 时使用默认映射
    origin: str = "manual"           # 数据来源标识
```

#### 4.3.3 画布交互设计

| 交互操作 | 触发方式 | 行为 |
|----------|----------|------|
| 平移画布 | 鼠标左键拖拽空白区域 | 改变 `viewOffset`，通过 `requestAnimationFrame` 实现流畅平移 |
| 缩放画布 | 鼠标滚轮 | 以鼠标位置为中心缩放，范围 10%~500% |
| 缩放控件 | 侧边栏 +/- 按钮 | 步进 20% 缩放，重置按钮恢复 1:1 |
| 节点拖拽 | 鼠标拖拽节点 | 实时更新坐标，松手后自动保存 |
| 选中节点 | 点击节点 | 高亮卡片，侧边栏显示属性编辑器 |
| 选中边 | 点击边标签 | 高亮边线，侧边栏显示边信息 |
| 右键菜单-画布 | 右键空白 | 新增独立知识概念 |
| 右键菜单-节点 | 右键节点 | 新增子概念 / 从此节点连线 / 折叠/展开子节点 |
| 连线模式 | 点击"关系连线"→点击源节点→点击目标节点 | 输入关系名后创建有向边 |
| 新增子概念 | 选中父节点后点击"新增子概念" | 新节点自动置于父节点下方，自动创建父子边 |
| 折叠/展开 | 右键含子节点的节点 | 隐藏/显示所有后代节点 |

#### 4.3.4 连线渲染算法

- **父子关系边**：树状正交折线（Orthogonal Line），由三段线段组成
- **普通关系边**：二次贝塞尔曲线，自然弯曲避免重叠
- **端点计算**：使用射线-矩形求交算法（`lineRectIntersection`），确保连线端点落在节点卡片边框上
- **权重显示**：边标签格式为 `关系名 · 权重%`

#### 4.3.5 符号格式化

系统内置工程符号渲染逻辑（`formatSymbol`），自动识别物理量符号并应用上下标格式：
- 下划线模式：`Q_p` → Q<sub>p</sub>
- 数字下标：`CO2` → CO<sub>2</sub>
- 常见工程后缀：`TDSin` → TDS<sub>in</sub>

### 4.3A 知识检索模块

#### 功能描述

提供单项目内跨维度的知识检索能力：在指定项目的知识图谱上，按关键词对知识概念名称、概念属性、
关系名称与数据来源四类维度做大小写不敏感的包含匹配，结果按"知识概念"与"知识关系"分组返回，
并支持点击结果在知识建模画布中定位与高亮。

#### 接口定义

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/knowledge/search` | 知识检索。参数：`project_id`（必填）、`q`（必填，关键词）、`scope`（可选，逗号分隔：`concept`/`attribute`/`relation`/`source`，默认 `all`）、`limit`（可选，1~200，默认 50） |

#### 响应要点

- `concepts[]`：命中的知识概念，含 `match_field`（`name`/`attribute`/`source`）、`match_snippet`（命中字段完整原值）、`parent_path`（祖先路径）
- `relations[]`：命中的知识关系，含 `source_name`/`target_name`（真实概念名）、`match_field`（`relation`/`source`）
- `total`：本次实际返回条数（受 `limit` 截断），非命中总数

#### 实现要点

- 复用 `main.py` 的项目数据加载函数读取 `GraphState`
- 为避免循环导入，`backend/app/routers/knowledge.py` 在函数体内延迟导入 `_load_project_data`
- 项目不存在时返回空结果集（HTTP 200），不抛异常
- 全空白关键词（strip 后为空）提前返回空结果集，避免 `"" in s` 恒真导致误命中全部数据

### 4.4 知识采集模块（OCR 实体提取）

#### 4.4.1 功能描述

从图片、文本文件、CSV 文件中自动识别文字并提取中文名词实体，作为知识概念的候选词导入画布。

#### 4.4.2 支持的文件类型

| 文件类型 | 扩展名 | 处理方式 |
|----------|--------|----------|
| 图片 | .png, .jpg, .jpeg, .bmp, .webp | RapidOCR 文字识别 → 表格/文本分类 → 实体抽取 |
| 文本 | .txt, .md | 直接读取内容 → jieba 分词 → 名词实体抽取 |
| CSV | .csv | 解析行列 → 单元格实体抽取 |

#### 4.4.3 OCR 表格/文本自动分类算法

1. OCR 识别结果按 Y 坐标分组为行
2. 计算每行单元格数量的中位数
3. 判断条件：行数 ≥ 3、中位列数 ≥ 3、密集行占比 ≥ 60% → 判定为表格
4. 表格模式：提取每个非数字、非标题单元格作为实体
5. 文本模式：拼接所有文字 → jieba 词性标注 → 提取名词（n*）和英文（eng）词汇

#### 4.4.4 实体抽取策略

```python
def _extract_nouns_from_text(text: str) -> list[str]:
    # 1. 正则提取英文符号（如 cutting_speed, spindle_rpm）
    # 2. jieba 分词 + 词性标注，提取名词（n*）和英文词（eng）
    # 3. 去重保持原始顺序
    # 4. 无名词时回退到分句策略
```

#### 4.4.5 实体导入布局

导入的实体自动按 4 列网格布局排列在画布上，支持指定父节点（所有导入实体作为其子节点）。

### 4.6 贝叶斯网络分析模块

#### 4.6.1 功能描述

基于知识关系网络和因果概率权重，提供三种贝叶斯分析能力：上游追溯、下游传播和全局概览。

#### 4.6.2 权重模型

```python
def _get_edge_weight(edge, relation_weights):
    if edge.weight is not None:
        return edge.weight          # 显式覆盖（每条边可单独设权重）
    return relation_weights.get(edge.relation, 0.5)  # 按关系类型默认映射
```

权重配置示例：
```json
{
  "控制": 0.80,
  "影响": 0.50,
  "决定": 0.90,
  "关联": 0.30
}
```

#### 4.6.3 扩展有向图构建

分析前构建扩展邻接表，包含：
1. **显式关系边**：用户手动创建的 relation 类型边
2. **推理推导边**：依据推理规则迭代推导的间接边（BFS 传播，最多 10 轮）
   - 推导边概率 = 两段路径概率的乘积
   - 标记 `is_derived=True` 以区别于原始边

#### 4.6.4 上游追溯算法

- **输入**：目标节点 ID
- **算法**：
  1. 构建扩展邻接表
  2. 对每个非目标节点，DFS 搜索所有到达目标的简单路径（无重复节点）
  3. 路径概率 = 路径上所有边权重的乘积
  4. 多路径合并 = Noisy-OR 模型：P_combined = 1 - ∏(1 - P_i)
  5. 按合并概率降序排列
- **影响力等级映射**：
  - P ≥ 0.8 → "很高"
  - P ≥ 0.6 → "高"
  - P ≥ 0.4 → "中等"
  - P < 0.4 → "较低"

#### 4.6.5 下游传播算法

- **输入**：源节点 ID
- **算法**：
  1. BFS 从源节点出发，找出所有可达节点
  2. 对每个可达节点，DFS 搜索最优路径
  3. Noisy-OR 合并 → 影响力等级判定
  4. 按合并概率降序排列

#### 4.6.6 全局概览算法

- **影响力排名**：对每个节点 BFS 计算可达节点数 + 最大出边权重
- **脆弱性排名**：统计每个节点的入边数量，降序排列
- **最强因果链**：从影响力前 10 的节点出发，寻找跨越多节点的长路径（≥2 跳），取概率最高的 10 条
- **总结文本**：自动生成分析结论

#### 4.6.7 路径可视化

分析结果通过画布联动高亮展示：
- 提取路径中所有节点名称 → 映射到节点 ID → 高亮对应卡片
- 非高亮节点半透明降低视觉权重
- 清除按钮取消高亮恢复默认状态

### 4.7 规则引擎模块

#### 4.7.1 推理规则

**数据模型**：
```python
class InferenceRule(BaseModel):
    id: str
    rel1: str      # 前件关系
    rel2: str      # 后件关系
    inferred_rel: str  # 推导关系
```

**语义**：若存在 `A →(rel1)→ B` 且 `B →(rel2)→ C`，则自动推导 `A →(inferred_rel)→ C`

**示例**：
```
rel1="控制", rel2="影响", inferred_rel="决定"
→ 若 "预热温度→控制→精馏塔" 且 "精馏塔→影响→产品质量"，
  则推导 "预热温度→决定→产品质量"
```

**触发时机**：每次创建新关系边时，自动执行 BFS 推理传播

#### 4.7.2 互斥规则

**数据模型**：
```python
class MutexRule(BaseModel):
    id: str
    rel1: str
    rel2: str
```

**语义**：同一对节点（source→target）之间，不能同时存在 `rel1` 和 `rel2` 两种关系

**触发时机**：创建新关系边时校验，如果目标节点对已存在互斥关系则拒绝创建

### 6.3 文件编码处理

系统对上传文本文件实施多层编码检测与回退策略：

1. 检测 BOM（UTF-8-BOM / UTF-16-LE / UTF-16-BE）
2. UTF-8 严格解码
3. 零字节比例 > 15% → UTF-16 尝试
4. 中文本地编码回退（GB18030 → GBK → BIG5）
5. 最终回退 UTF-8 replace 模式

## 8. 安全设计

### 8.1 认证与授权

- **认证方式**：基于用户名/密码的 Token 认证
- **Token 管理**：UUID 随机生成，存储在内存字典中，服务重启后失效
- **会话持久化**：前端 localStorage 存储 Token，启动时验证有效性
- **角色控制**：前端根据 `role` 字段控制 UI 元素的可见性和可操作性

### 8.2 数据安全

- **密码存储**：当前以明文存储于 Excel 文件（`users.xlsx`），适用于内网隔离环境
- **项目数据隔离**：每个项目独立 JSON 文件，通过 project_id 参数访问
- **文件上传安全**：
  - 文件类型白名单（.xlsx, .xls, .csv）
  - UUID 重命名避免路径遍历
  - 上传目录独立于项目数据

### 8.3 网络安全

- **CORS**：当前配置 `allow_origins=["*"]`，适用于内网开发环境
- **后端监听**：
  - 开发模式：`--host 127.0.0.1`（仅本机）
  - 打包模式：`host="0.0.0.0"`（但通过 start.bat 启动时也监听 127.0.0.1）
- **API 代理**：前端 Vite dev server 通过 proxy 转发 API 请求，浏览器不直接暴露后端端口

### 8.4 输入验证

- 所有 API 请求通过 Pydantic 模型进行类型校验和约束检查
- 节点名称不能为空（`min_length=1`）
- 关系名称不能为空
- 防止自环连接（source ≠ target）
- 防环检测（reparent 时检查不会形成循环层级）
- 项目名称长度限制（1-100 字符）

### 9.3 端口分配策略

- 前端端口：5173-5200 范围扫描，选第一个可用端口
- 自动结束占用端口的残留进程
- 通过环境变量 `VITE_BACKEND_PORT` 传递后端端口给前端

### 10.3 已知限制与改进方向

**当前限制**：
- 单用户模式，不支持多人并发编辑

- Noisy-OR 模型假设路径独立性，在大规模循环图中可能存在精度偏差
- 没有操作日志和版本历史

**改进方向**（来自 README）：
- OWL / RDF 标准知识表示格式导入导出
- 大语言模型（LLM）辅助实体识别
- 更多数据库类型支持（MySQL、PostgreSQL 等）
- 多人协同编辑
- 版本历史与回退
- 自定义知识模板
